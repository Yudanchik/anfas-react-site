# Часть 1. Бизнес-требования

> Эта часть описывает цели, сценарии и ограничения продукта.  
> Она **не привязана к конкретным технологиям** и должна сохранять смысл при смене стека.

## 1.1. Цели раздела

Раздел «Прайс-лист» решает одновременно три задачи:

1. **Органический трафик** — страницы с ценами на виды работ должны находиться и индексироваться поисковыми системами.
2. **Удобство для посетителя** — понятные категории и ориентиры по стоимости без необходимости сразу запрашивать полный документ.
3. **Лидогенерация** — получение контактов в обмен на полный прайс-лист и дальнейшая коммуникация по смете.

Полный прайс-лист заказчика существует как объёмный документ (сотни позиций). На сайте он **не публикуется целиком** в открытом виде.

## 1.2. Бизнес-задачи

- Показать посетителю **структуру работ** и **ориентировочные цены** по ключевым категориям.
- Сохранить коммерческую ценность полного прайса: файл доступен только после заявки.
- Автоматически доставлять полный прайс заявителю после успешной отправки формы.
- Уведомлять компанию о каждой заявке на прайс.
- Дать возможность обновлять полный прайс **без участия разработчика** на каждом изменении цен.
- Встроить раздел в общую воронку сайта: услуги, проекты, журнал, консультация.

## 1.3. Ограничения контента

- На сайте публикуется только **превью**: категории и ограниченный набор популярных позиций (порядка 10–20 на категорию).
- Полный перечень позиций остаётся в защищённом полном прайсе.
- Служебные и узкоспециальные блоки полного прайса (коэффициенты, вспомогательные работы и т.п.) не обязаны иметь отдельные посадочные страницы.
- Цены на сайте — **ориентир**; точная смета формируется после замера и уточнения объёма. Это должно быть явно сказано пользователю.

## 1.4. Информационная архитектура (продуктовая)

Раздел состоит из:

| Страница | Назначение |
|----------|------------|
| Хаб прайса | Обзор категорий, цены «от», призыв получить полный прайс |
| Страница категории | Углубление в один вид работ: превью позиций, пояснения, FAQ, CTA |
| Страница успешной заявки | Подтверждение отправки, дожим к консультации и другим разделам |

Категории — **самостоятельные посадочные сущности для поиска**, а не только фильтр на одной странице.

Примеры смысловых категорий (состав может уточняться при наполнении): вывоз мусора, гипсокартон, демонтаж, кладка, штукатурка, малярные работы, плитка, напольные покрытия, электромонтаж, сантехмонтаж, кондиционирование, звукоизоляция, потолки, двери, общестроительные работы.

## 1.5. Пользовательские сценарии

### Сценарий A. Изучение цен и запрос полного прайса

1. Пользователь открывает хаб прайса или сразу категорию (из поиска / меню / перелинковки).
2. Изучает категории и/или превью позиций.
3. Нажимает «Получить полный прайс».
4. Заполняет короткую форму (имя и телефон).
5. Отправляет заявку.
6. Видит подтверждение успеха.
7. Получает на почту письмо со ссылкой на скачивание полного прайса.
8. Скачивает файл по ссылке в течение срока её действия.

### Сценарий B. Только ориентир, затем консультация

1. Пользователь смотрит превью цен.
2. Вместо полного прайса выбирает обсуждение сметы / консультацию.
3. Оставляет заявку через общий сценарий лида сайта.

### Сценарий C. Повторный запрос

1. Ссылка на скачивание истекла или письмо не найдено.
2. Пользователь снова запрашивает прайс через форму или связывается с компанией по контактам со страницы успеха.

### Сценарий D. Обновление прайса сотрудником компании

1. Подготовлен новый файл полного прайса.
2. Сотрудник заменяет файл по согласованной инструкции сопровождения.
3. При существенном изменении публичных ориентиров обновляется превью на сайте (реже, чем замена файла).

## 1.6. UX

### Принципы

- Сначала ценность (понятные цены «от»), затем обмен контакта на полный документ.
- Форма запроса прайса — **минимальная** (имя, телефон), без лишних полей.
- Ошибки валидации — у полей; ошибка отправки — заметное сообщение без потери введённых данных (где это возможно).
- Успех — не одно слово «Спасибо»: объяснить, что письмо уже ушло, куда смотреть (в т.ч. «Спам»), что делать дальше.
- Повторная отправка формы допускается; злоупотребления ограничиваются правилами защиты (см. ниже).

### Ключевые экраны

**Хаб:** заголовок раздела, краткий lead, сетка категорий с ценой «от», общий FAQ, основной CTA на полный прайс, вторичные ссылки на услуги и проекты.

**Категория:** хлебные крошки, заголовок категории, lead, таблица/список превью, дисклеймер про ориентир, блок «что влияет на цену», FAQ категории, CTA на полный прайс и на обсуждение сметы, связанные материалы сайта.

**Успех:** подтверждение отправки письма, контакты на случай проблем с почтой, подборка проектов, ссылки на услуги и журнал, повторный призыв обсудить смету.

### Состояния формы

- Простой ввод → отправка (состояние ожидания на кнопке) → успех или ошибка.
- Защитное скрытое поле от ботов не показывается человеку.

## 1.7. SEO-концепция

### Зачем отдельный раздел

Поисковый спрос на «цены / стоимость работ» не должен закрываться только PDF. Индексируется **HTML-контент** раздела: категории, превью позиций, поясняющие тексты, FAQ.

### Структура для поиска

- Хаб отвечает на общие запросы о ценах на ремонт.
- Страницы категорий отвечают на узкие коммерческие запросы по видам работ.
- Полный PDF **не является** посадочной страницей и не должен индексироваться как открытый документ сайта.

### Содержание страниц

- Уникальные заголовок и описание для хаба и каждой категории.
- Один главный заголовок страницы; логичная иерархия подзаголовков.
- Видимые цены «от» и единицы измерения в превью.
- FAQ с полезными ответами (не только для разметки).
- Внутренние ссылки на услуги, проекты, журнал и обратно на прайс.
- Хлебные крошки: главная → прайс-лист → категория.

### Что не индексируем как отдельные витрины

- Страница успешной заявки.
- Служебные URL выдачи файла.
- URL с маркетинговыми метками (обрабатываются общими правилами сайта).

## 1.8. Лидогенерация

- Основной оффер раздела: **полный прайс в обмен на контакт**.
- Каждая успешная заявка создаёт уведомление компании и письмо пользователю со ссылкой на файл.
- Источник заявки должен позволять отличать запрос прайса от прочих лидов (для учёта и обработки).
- После получения прайса воронка продолжается: смета, консультация, выбор формата работ.

## 1.9. Требования к безопасности

- Полный прайс **недоступен** по постоянному публичному адресу, который можно угадать или найти в поиске.
- Доступ к файлу — только после успешной заявки, по **временной** ссылке с ограниченным сроком жизни (ориентир — 24 часа).
- Простая пересылка «вечной» ссылки третьим лицам должна быть затруднена истечением срока.
- Выдача файла не должна поощрять индексацию поисковыми системами.
- Форма защищается от типового спама (скрытое поле, ограничение частоты, контроль времени заполнения — по мере необходимости без ухудшения UX для людей).
- Секреты и доступы к почте/файлу не хранятся в публичном репозитории клиентского кода.

## 1.10. Требования к производительности

- Страницы раздела должны открываться быстро: без загрузки полного прайса при просмотре категорий.
- Превью ограничено по объёму; тяжёлый файл загружается только в момент скачивания по ссылке.
- Раздел не должен заметно ухудшать показатели скорости ключевых страниц сайта.

## 1.11. Требования к сопровождению

- Замена полного прайс-файла — простая операция для сотрудника компании по инструкции.
- Публичные превью и SEO-тексты обновляются при существенном изменении цен или состава работ (планово, не при каждой мелкой правке файла).
- Дата/редакция прайса доносится пользователю там, где это уместно («актуально на …»).

## 1.12. Аналитика (продуктовые события)

Необходимо измерять воронку раздела:

- просмотр хаба;
- просмотр категории;
- открытие формы запроса прайса;
- попытка отправки формы;
- успешная отправка;
- просмотр страницы успеха.

Скачивание файла по письму может учитываться упрощённо или на следующем этапе — без усложнения первого запуска.

## 1.13. Нефункциональные ожидания

- Поведение и тексты раздела согласованы с тоном бренда Анфас.
- Раздел доступен с мобильных устройств (читаемые таблицы/списки превью, удобный CTA).
- Ошибки доставки письма пользователю не должны оставлять компанию без уведомления о лиде.

# Архитектурные решения (ADR)

Ниже зафиксированы решения, принятые на этапе проектирования.  
Обоснования краткие; смена решения требует явного пересмотра документа.

### ADR-01. Отдельный раздел сайта «Прайс-лист»

**Решение:** Выделить самостоятельный раздел с собственной точкой входа в навигации.  
**Обоснование:** Цены — отдельный коммерческий интент; смешивание только с услугами или журналом снижает и SEO, и ясность оффера.

### ADR-02. Отдельные SEO-страницы категорий

**Решение:** У каждой выбранной категории работ — собственная индексируемая страница, а не только фильтр на хабе.  
**Обоснование:** Узкие запросы («демонтаж», «электромонтаж», «гипсокартон») требуют уникальных заголовков, текстов и превью.

### ADR-03. Курируемый набор категорий на сайте

**Решение:** На сайт выносятся не все разделы полного прайса, а отобранные SEO-значимые категории (ориентир 12–15).  
**Обоснование:** Служебные блоки прайса не дают поисковой ценности и размывают структуру.

### ADR-04. Превью цен хранится отдельно от полного прайса

**Решение:** На страницах показывается ограниченный список позиций; полный перечень живёт только в защищённом файле.  
**Обоснование:** Баланс между индексацией, удобством и защитой коммерческого документа.

### ADR-05. Полный прайс недоступен для индексации как открытый файл

**Решение:** Файл не публикуется по постоянному открытому URL в статике сайта.  
**Обоснование:** Иначе полный прайс уходит в поиск и теряет ценность как лид-магнит.

### ADR-06. Полный прайс выдаётся только после отправки формы

**Решение:** Скачивание возможно только после успешной заявки с контактами.  
**Обоснование:** Основная модель лидогенерации раздела.

### ADR-07. Пользователь получает ссылку по электронной почте

**Решение:** После заявки пользователю уходит письмо со ссылкой на скачивание (не обязательная отправка файла вложением в первом релизе).  
**Обоснование:** Лучше доставляемость и контроль срока доступа; компания параллельно получает уведомление о лиде.

### ADR-08. Ссылка на скачивание ограничена по времени

**Решение:** Срок жизни ссылки ограничен (ориентир 24 часа), доступ без валидной ссылки невозможен.  
**Обоснование:** Снижает риск «вечной» раздачи файла.

### ADR-09. Единая форма заявок сайта

**Решение:** Запрос прайса идёт через общий механизм лидов сайта с отдельным сценарием/источником «прайс», без параллельной «второй CRM-формы».  
**Обоснование:** Единый учёт заявок, меньше дублирования UX и поддержки.

### ADR-10. Страница успеха после заявки на прайс

**Решение:** Помимо короткого подтверждения в интерфейсе формы есть отдельная страница успеха с дожимом.  
**Обоснование:** Рост конверсии в консультацию и переходы в проекты/услуги.

### ADR-11. Категории — часть SEO, служебные URL — нет

**Решение:** Индексируются хаб и категории; страница успеха и выдача файла — нет.  
**Обоснование:** В индекс попадает коммерчески полезный контент, не служебные шаги воронки.

### ADR-12. Сопровождение файла полного прайса без разработчика

**Решение:** Замена файла полного прайса выполняется сотрудником по инструкции; частые правки не требуют релиза приложения.  
**Обоснование:** Прайс обновляется чаще, чем код сайта.

### ADR-13. Перелинковка с услугами, проектами и журналом

**Решение:** Раздел цен связан внутренними ссылками с остальными коммерческими разделами.  
**Обоснование:** Усиление SEO и перевод трафика с цен в заявку на ремонт.

# Часть 2. Техническая реализация (текущая архитектура)

> **Важно:** раздел описывает реализацию **для текущей версии архитектуры** проекта Анфас.  
> После проведения архитектурного аудита техническая часть может быть пересмотрена.  
> **Часть 1 (бизнес-требования) и пользовательские сценарии при этом остаются в силе.**

## 2.1. Контекст текущей архитектуры

- Клиент: React Router Framework Mode, статическая генерация (prerender) явных URL, `ssr: false`.
- Слои: FSD — `routes → widgets → features → entities → shared`.
- Контент сущностей: локальные данные TypeScript + repository (как статьи, проекты, услуги).
- Лиды: `BriefModal` / `ModalTriggerButton` / `OpenLeadForm` → `submitLead` → `POST /api/lead.php` → SMTP Mail.ru.
- Хостинг писем и PHP: REG.RU (локальный `pnpm dev` PHP не исполняет).
- SEO: `createSeoMeta`, ручные `sitemap.xml` / prerender / `robots.txt`, JSON-LD точечно.
- Аналитика: Яндекс Метрика (hit на смене маршрута есть; `reachGoal` для лидов пока не подключён).

## 2.2. URL и маршруты

| `/prices` | Хаб | index |
| `/prices/:categorySlug` | Категория | index |

Регистрация в `src/routes.ts`, пути в `react-router.config.ts` (prerender), записи в `public/sitemap.xml` (кроме thanks или thanks без индексации).

Пункт навигации и футера: `src/shared/config/company.ts`.  
Glass-hero для `/prices`: расширить условие в `SiteHeader`.

## 2.5. Форма и лид

- Новый intent `price-list` в `src/features/brief/model/lead-modal.ts` + тексты preset.
- Открытие через существующий `ModalTriggerButton` / `openLeadModal`.
- Поля: имя, телефон, honeypot `company`; `service` — из allowlist (как минимум `general`).
- `source`: `prices-hub`, `prices-{slug}`, `prices-thanks`.
- После успеха — переход на `/prices/thanks` (плюс короткий success в модалке).
- Доработать клиент: передача `startedAt` в `submitLead` (серверная проверка уже есть в `lead.php`).
- Подключить `ym(..., 'reachGoal', ...)` для событий воронки (в т.ч. использовать `analyticsEvent`).

## 2.6. Backend (PHP на текущем хостинге)

### Доработка `public/api/lead.php`

- Распознавание заявки на прайс (intent/source).
- Письмо **в офис** (как сейчас) с пометкой «запрос полного прайса».
- Письмо **пользователю** со ссылкой скачивания.
- Генерация токена доступа (HMAC: идентификатор заявки / контакта + `exp` + секрет).
- Rate limit по IP (например, лимит заявок в час).
- Конфиг в `config.local.php` (не в git): путь к PDF, секрет, TTL (86400), параметры писем.

### Новый `public/api/price-download.php`

- Проверка подписи и срока.
- Stream файла, `Content-Disposition: attachment`.
- Заголовок запрета индексации ответа.
- Файл вне публичной раздачи: `public/api/private/` + deny в `.htaccess` (или путь вне web root на сервере).

### Почта

- Остаёмся на **Mail.ru SMTP** через существующий механизм (см. `docs/LEAD_FORM_EMAIL.md`).
- Предпочтительно ссылка в письме, не вложение PDF.
- Письмо: текстовая часть + простой HTML в фирменных цветах, срок действия ссылки, контакты.

## 2.7. SEO (технический слой)

## 2.8. Производительность (в рамках текущего стека)

- Prerender хаба и всех категорий.
- PDF не загружается на просмотре страниц.
- Превью — десятки строк, не сотни.
- Обложки категорий — webp в `public/images/prices/` при необходимости.
- Модалка лида уже подключается лениво в корне приложения.

## 2.9. Сопровождение PDF (операционка)

1. Сотрудник загружает новый файл на сервер по фиксированному пути (например `api/private/anfas-price-list.pdf`) через FTP / файловый менеджер хостинга.
2. При необходимости обновляет дату редакции в конфиге/метафайле на сервере.
3. Сильное изменение ориентиров на сайте — правка `prices.data.ts` и релиз статики.
4. Инструкция для заказчика: отдельный короткий ops-документ (например `docs/PRICE_LIST.md`) после старта реализации.

Файл полного прайса **не обязан** храниться в git.

# Возможные изменения после архитектурного аудита

После аудита могут измениться **технические** способы реализации.  
**Бизнес-требования, UX-сценарии, SEO-концепция и ADR продуктового уровня (§1 и ADR-01…13 по смыслу продукта) остаются обязательными**, пока отдельно не пересмотрены бизнесом.

Могут быть пересмотрены:

| Область | Примеры смены реализации |
|---------|---------------------------|
| Backend | Node API, serverless вместо PHP |
| CMS | Внешняя CMS для превью и текстов |
| База данных | Хранение позиций и заявок в БД |
| Файловое хранилище | Object storage вместо файла на хостинге |
| Отправка email | Другой транзакционный провайдер |
| Хранение PDF | Bucket + signed URL |
| Хранение заявок | CRM / очередь / БД вместо только письма в офис |
| Аналитика | Другой стек событий / CDP |
| Рендеринг | SSR/ISR вместо текущего prerender-SPA |

При смене реализации обновляется **только Часть 2** (и при необходимости формулировки ADR технического характера), с новой версией документа.
