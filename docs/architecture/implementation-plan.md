## 1. Рамки и источники истины

План основан только на:

- [`target-architecture.md`](target-architecture.md)
- [`price-list.md`](price-list.md)

Зафиксированное уточнение спецификации: поле **email обязательно только для формы с `intent="price-list"`**, поскольку ссылка на полный PDF отправляется пользователю по электронной почте. Остальные формы сайта сохраняют текущие поля.

Реализация v1 сохраняет React Router Framework Mode, `ssr: false`, явный prerender, FSD и Repository Pattern. Публичное превью хранится во frontend; полный PDF — вне web root в приватном ops-хранилище. CMS, база данных, интернет-магазин и личный кабинет в объём v1 не входят.

Также вне v1 остаются автопарсинг PDF, поиск по полному прайсу, captcha без фактической спам-проблемы и отдельная аналитика скачивания файла.

## 2. Предварительные условия

Перед этапом 1 исполнителю должны быть доступны:

- актуальный PDF заказчика как источник наполнения превью; он не коммитится в репозиторий;
- согласованные 15 slug из Design Document;
- доступ к dev-стенду REG.RU для финальной проверки PHP/SMTP;
- отдельный тестовый PDF для dev-контура.

Если актуального PDF нет, этап 1 блокируется: придумывать цены нельзя.

- Вызов Метрики безопасен при отсутствии `window.ym` и во время prerender.
- Ошибка API сохраняет введённые данные и не отправляет success-goal.
- `pnpm check` проходит.

## Этап 3. Backend: dual-mail и защищённая выдача PDF

### Цель

Реализовать целевой ops-поток: заявка уведомляет офис, пользователь получает временную ссылку, а PDF нельзя скачать по постоянному публичному URL.

### Краткое описание

Расширить существующий PHP endpoint без создания второго lead-контура:

- распознавать `intent="price-list"`;
- валидировать email только для этого intent;
- сохранять текущую allowlist услуг;
- применять honeypot, `startedAt` и файловый rate limit по хешу IP;
- сначала отправлять письмо в офис с пометкой «Запрос полного прайса»;
- затем отправлять пользователю text+HTML письмо со ссылкой и сроком действия;
- генерировать случайный request id, `exp` и HMAC-подпись без контактов в URL.

Создать download endpoint, который проверяет формат параметров, HMAC и TTL, затем stream-ит настроенный PDF как attachment с `X-Robots-Tag`, `no-store` и `nosniff`.

Принять конкретную v1-модель хранения из допустимых Design Document: PDF лежит **вне web root** по абсолютному пути из `config.local.php`. В git и `build/client` файла нет.

### Новые файлы

- `public/api/price-download.php`

### Изменяемые файлы

- `public/api/lead.php`
- `public/api/config.example.php`
- `public/api/.htaccess`

### Зависимости

Зависит от payload-контракта этапа 2: `intent`, `email`, `startedAt`, `source`, `page`.

### Ожидаемый результат

Старые заявки продолжают отправлять одно письмо в офис. Заявка на прайс отправляет офисное письмо и отдельное клиентское письмо с HMAC-ссылкой примерно на 24 часа. Без валидной подписи или после истечения PDF не выдаётся.

### Критерии завершения

- Для обычного лида email не требуется; существующий API-контракт не сломан.
- Для `price-list` невалидный/пустой email даёт 422.
- Конфиг содержит примеры `price_pdf_path`, `price_link_secret`, `price_link_ttl=86400`, `public_site_url`, лимита и writable rate-limit path; реальные значения не коммитятся.
- URL не содержит email или телефон.
- Подмена `id`, `exp` или `sig` делает ссылку невалидной; сравнение подписи timing-safe.
- Истёкшая ссылка возвращает корректный 4xx и не раскрывает серверный путь.
- PDF stream содержит `Content-Type: application/pdf`, `Content-Disposition: attachment`, `X-Robots-Tag: noindex, nofollow, noarchive`, `Cache-Control: private, no-store`.
- Ошибка клиентского письма не отменяет уже доставленное уведомление офису и возвращает понятную ошибку без утечки SMTP-деталей.
- Rate limit не блокирует все IP общим счётчиком и не хранит сырой IP в публичном файле.
- `php -l` проходит для обоих endpoint’ов (если PHP доступен локально); иначе синтаксис проверяется на dev-стенде до публикации frontend.

## Общие принципы реализации UI

Этот раздел является обязательным для всех последующих этапов, содержащих пользовательский интерфейс (Этапы 4–7).

### 1. Использование существующей дизайн-системы

Все новые страницы раздела «Прайс-лист» должны использовать существующую дизайн-систему проекта.

Новые страницы должны выглядеть как естественное продолжение существующего сайта.

Не создавать новый визуальный стиль.

Использовать существующие:

- Layout
- Header
- Footer
- UI-компоненты
- типографику
- SCSS architecture
- переменные
- миксины
- адаптивные паттерны
- анимации

Не создавать новые дизайн-паттерны, если аналог уже существует в проекте.

### 2. Формирование открытого превью

Открытая часть категории не должна быть механической копией первых строк PDF.

Необходимо сформировать небольшую витрину категории.

Показывать наиболее понятные, коммерчески востребованные и полезные пользователю услуги.

При выборе учитывать:

- понятность;
- коммерческую ценность;
- поисковый интент пользователя;
- разнообразие услуг внутри категории.

### 3. Количество отображаемых услуг

Для каждой категории отображать ориентировочно 10–20 публичных услуг.

Полный перечень услуг никогда не публикуется.

### 4. Отображение цен

Открытые услуги отображаются вместе с реальными ценами.

Скрывается не стоимость услуг, а полный объём прайс-листа.

После публичного списка пользователь должен видеть сообщение о том, что полный прайс содержит значительно больше позиций.

Далее должно следовать предложение получить полный PDF.

### 5. Консистентность реализации

Все UI-этапы должны руководствоваться данным разделом.

Agent не должен самостоятельно менять:

- стиль страниц;
- количество отображаемых услуг;
- структуру открытого превью;
- принципы отображения данных;
- UX получения полного прайс-листа

без изменения утверждённой архитектурной документации.

### 6. Общий UX

Во всех последующих этапах придерживаться принципа:

«Минимум новых пользовательских сценариев, максимум повторного использования уже существующих компонентов и UX-паттернов проекта».

## 3. Проверка оптимальности последовательности

Последовательность оптимальна по следующим причинам:

1. **Контракты раньше UI:** этап 1 фиксирует домен, этап 2 — frontend payload, этап 3 — server contract. Поэтому страницы не строятся поверх временных типов.
2. **Backend раньше публичного CTA:** после этапа 3 форма уже имеет рабочий принимающий контур; хаб не публикуется с неработающей выдачей.
3. **Presentation отделён от routes:** этап 4 создаёт widgets без изменений глобальной маршрутизации; хаб и категория затем компонуются независимо.
4. **Хаб раньше категорий:** сначала появляется корневая навигация и общий SEO-контекст; этап 6 добавляет только динамическую ветку.
5. **Thanks после основного маршрута:** перенаправление подключается только после готового служебного URL.
6. **Ops и QA в конце:** документация описывает уже фактический контракт, а acceptance не маскирует незавершённые части.

## 4. Независимость и пересечения задач

- Этапы 1 и 2 могут разрабатываться параллельно, но перед этапом 4 оба должны быть завершены.
- Этап 3 может выполняться отдельным Agent Mode после фиксации payload этапа 2.
- Этап 4 создаёт только новые widget-файлы и не пересекается с routes.
- Этапы 5–7 по необходимости пересекаются только в централизованных файлах `src/routes.ts` и `react-router.config.ts`; объединять их в одну крупную задачу нецелесообразно.
- `public/sitemap.xml` меняется только на этапах 5 и 6; thanks намеренно туда не добавляется.
- Backend-файлы меняются только на этапе 3; операционные docs — только на этапе 8.
- Этапы 9–10 являются проверочными и не расширяют scope.

Каждый этап должен передаваться Agent Mode отдельным запросом с указанием номера этапа, ссылками на две спецификации и запретом выполнять последующие этапы.
