## 0. План роста продукта (вводные v1.1)

Эти факты **не меняют** описание текущего кода (§1), но **перекалибровывают** риски и очерёдность (§2–15).

| Сущность / область | План | Вывод для архитектуры |
|--------------------|------|------------------------|
| **Услуги** | +5–10 позиций, затем каталог почти закрыт | Не драйвер роста; **можно долго держать в коде** |
| **Основные страницы / дизайн** | Меняются крайне редко, структура утверждена | Витрина и layout — стабильны; не повод для CMS «всего сайта» |
| **Интернет-магазин** | Не планируется (нет оплаты, корзины, ЛК) | Не нужен commerce-backend, платежи, аккаунты покупателей |
| **Журнал** | ~**2 статьи в неделю** — главная SEO-стратегия | **Главный драйвер** выноса контента из frontend |
| **Проекты** | ~**1 проект в месяц**, много изображений | **Второй драйвер**; упор на медиахранилище + затем CMS |

Оценка объёма при заявленном темпе:

- Журнал: ≈ 8 статей/мес. → ≈ **100 статей/год** (плюс текущие 6).
- Проекты: ≈ **12 проектов/год**; при 20–40 фото на кейс — сотни новых файлов в год.

При таком темпе модель «статья = правка TypeScript + prerender + sitemap + деплой» **не выдержит редакционный ритм** уже через 1–3 месяца активных публикаций.

## 1. Анализ текущей архитектуры

### 1.1. Стек технологий

| Слой | Факт |
|------|------|
| UI | React 19, TypeScript |
| Роутинг / сборка | React Router 7 Framework Mode, Vite 6 |
| Стили | SCSS Modules (+ legacy в globals) |
| Формы | react-hook-form + Zod |
| Анимация / слайдеры | Framer Motion, Swiper |
| Пакетный менеджер | pnpm 11, Node ≥ 24 |
| «Server state» в package.json | `@tanstack/react-query` — **установлен, в коде не используется** |
| Бэкенд на проде (REG.RU) | PHP: `public/api/lead.php` + SMTP Mail.ru |
| Контейнеры | Dockerfile + compose в `deploy/vps/` (ручной workflow), основной прод — FTP статики |

### 1.2. Режим рендеринга (важно)

В `react-router.config.ts`:

- **`ssr: false`** — нет Node SSR в проде.
- Есть явный список **`prerender`** (~20+ URL): при `pnpm build` для них генерируется HTML в `build/client/.../index.html`.
- Остальные клиентские переходы работают как SPA; холодный заход / бот на URL без prerender зависит от rewrite хостинга.

Это **не** App Router Next.js и **не** классический Pages Router. Ближайшая аналогия: **статический маркетинг-сайт с prerender + SPA-навигацией**.

На REG.RU Host-0 **нет долгоживущего Node-процесса** — архитектура сознательно подогнана под статику + PHP.

### 1.3. Структура директорий (FSD-подобная)

```text
src/
  app/          # провайдеры
  routes/       # URL, meta, loader, композиция страниц
  widgets/      # крупные блоки UI (home, blog, header, …)
  features/     # сценарии: brief (заявки), faq
  entities/     # article, project, service, process
  shared/       # UI, hooks, config, styles
public/         # статика, sitemap, robots, api/*.php, галереи
docs/           # операционная документация
deploy/         # REG.RU, VPS
.github/workflows/
```

Заявленное направление зависимостей (`ARCHITECTURE.md`):  
`routes → widgets → features → entities → shared`.

**Отклонение:** `shared/ui/open-lead-form` импортирует `@/features/brief/*` (слой shared тянет features вверх по правилам FSD).

### 1.4. Маршрутизация

Файл `src/routes.ts` — декларация маршрутов:

- `/` home  
- `/about`, `/contacts`, `/cookies`, `/privacy`  
- `/blog`, `/blog/:slug`  
- `/projects`, `/projects/:slug`  
- `/services`, `/services/:slug`  
- `*` — 404  

Паттерн: **листинг + деталь по slug**. Категории блога — query `?tema=` (не отдельный path).

### 1.5. Организация страниц и компонентов

- Тонкие `routes/*/route.tsx`: `meta`, иногда `loader`, сборка виджетов.
- Виджеты home разбиты по секциям (hero, services, calculator, FAQ, …).
- Журнал: `widgets/blog` + `widgets/article`.
- Общие CTA заявок: `ModalTriggerButton`, `BriefModal`, `OpenLeadForm`.

### 1.6. Данные и загрузка

| Механизм | Где |
|----------|-----|
| `loader` + repository | blog, article, projects, project, service |
| Repository → `local*Repository` | читает `*.data.ts` **на этапе сборки/рантайма бандла**, без HTTP CMS |
| Без loader | home, about, contacts, legal — импорт виджетов и статики |
| Сеть | только `POST` заявки на `/api/lead.php` |

Интерфейсы repository уже намекают на смену источника (в т.ч. комментарии про WordPress для проектов), но **второй реализации нет**.

### 1.7. Контент и медиа

- Тексты сущностей — в TypeScript.
- Галереи проектов и обложки блога — `public/images/...` (пути прописаны в data-файлах).
- Часть UI-картинок — `src/assets` (через Vite).
- Крупный `public/videos/hero.mp4` заметно раздувает объём `public/`.

### 1.8. Инфраструктура

| Канал | Назначение |
|-------|------------|
| CI | typecheck + eslint + stylelint + build |
| Deploy REG.RU | push `main`/`dev` → FTP `build/client` |
| Deploy VPS | вручную, Docker/GHCR |
| GitHub Pages | опционально, с `PUBLIC_PATH` |
| Секреты почты | `api/config.local.php` на сервере (не в git) |

**Расхождения документации и фактов:**

- `ARCHITECTURE.md` утверждает использование TanStack Query как server state — фактически нет.
- `docs/DEPLOYMENT.md` упоминает root `docker compose` — compose лежит в `deploy/vps/`.
- Sitemap и prerender уже расходились по составу URL (риск тройной синхронизации).
- В репозитории могут сосуществовать lockfile’ы разных менеджеров; CI ориентирован на pnpm.

### 1.9. Как проект устроен «одной фразой»

Маркетинговый сайт с **контентом в коде**, **SEO через prerender HTML**, **заявками через один PHP-скрипт на shared hosting**, слоями FSD на фронте и заделом repository без реального внешнего API контента.

| Проекты (7) + галереи | `projects.data.ts` + десятки/сотни webp | Да | Разработчик + релиз | **Больно по весу и спискам путей** |

### 2.2. Что уже «вне фронтенда»

- **Заявки** уходят на почту через PHP (контент заявки не в React state навсегда).
- Секреты SMTP — на сервере.

### 2.3. Что выносить из frontend: приоритет с учётом плана роста (v1.1)

| Приоритет | Сущность | Действие | Почему |
|-----------|----------|----------|--------|
| **1** | **Статьи журнала** | Вынести в CMS/БД **первыми** | ~2 шт./нед. — основной рост и SEO; TS+деплой на каждую статью неприемлем |
| **2** | **Медиа проектов** (затем карточки проектов) | CDN / object storage → затем CMS | ~1 проект/мес., но тяжёлые галереи; git+FTP начнут тормозить раньше, чем «мало проектов» кажется проблемой |
| **3** | **Заявки как учёт** | Почта → CRM/БД по объёму лидов | Не связано с темпом статей; зависит от продаж |
| **4** | **Превью прайса** | Сначала по DD в коде/файле; в CMS — только если цены правят не-разработчики часто | Каталог услуг почти закрыт; полный PDF — ops-файл |
| **Оставить в коде надолго** | Услуги (до ~12 шт.), процесс, FAQ, партнёры, legal, copy основных страниц | Редек/дизайн утверждены; услуг мало | Нет смысла тащить в CMS «весь сайт» |
| **Не строить** | Каталог товаров, корзина, ЛК, оплата | Магазина не будет | Не раздувать backend под commerce |

**Итог инвентаризации v1.1:** вынос Urgency сместился с «когда вырастет» на **конкретный редакционный темп журнала**. Услуги и витрина — сознательно остаются в frontend.

## 3. Масштабируемость и технический долг

### 3.1. Готовность к росту

Архитектура **хорошо подходит** для:

- стабильной маркетинговой витрины (главная, услуги, about, contacts);
- небольшого фиксированного каталога услуг (+5–10 и стоп);
- SEO через prerender;
- дешёвого shared hosting для раздачи HTML/JS.

Архитектура **не готова** как редакция журнала при **2 статьях в неделю** и как медиатека портфолио при регулярных тяжёлых галереях — без выноса статей и изображений.

Отсутствие магазина **упрощает** картину: не нужны платежный контур, корзина, сессии покупателя.

### 3.2. Проблемные места на горизонте 3–12 месяцев (уточнено)

| Риск | Оценка с планом роста |
|------|------------------------|
| Журнал в TS | **Критический** при 2/нед. (~100 статей/год) |
| Тройная синхронизация prerender/sitemap | Усиливается каждым постом |
| Галереи проектов в git | **Высокий** при 1 проекте/мес. с десятками фото |
| Услуги в коде | **Низкий** риск |
| Правки основных страниц | **Низкий** (редко) |
| Commerce/ЛК | **Нет** (не планируется) |
| Заявки только в почте | Средний — зависит от лидогенерации, не от журнала |
| REG.RU без Node | CMS/API почти наверняка рядом (VPS/SaaS), статика может остаться на Host-0 |

### 3.3. Что желательно изменить уже сейчас (процессно)

- Готовить вынос **журнала** (контракт repository уже есть) — не откладывать «до 20 статей»: при 2/нед. порог наступит быстро.
- Для проектов заранее запретить бесконтрольный рост бинарников в git (политика хранения фото).
- Услуги и витрину **не** включать в первый эпик CMS.
- Прайс v1 — в текущей архитектуре (отдельный DD), не блокируя пилот CMS журнала.

## 4. Нужен ли полноценный backend

### 4.1. Определение

Под «полноценным backend» здесь понимается **сервис приложения** (API + бизнес-логика + хранение), а не единственный PHP mailer.

### 4.2. Сейчас

Backend по сути **узкий**: приём заявки и SMTP. Контент собирается на этапе фронтенд-сборки.

### 4.3. Нужен ли полноценный backend?

**Не как срочная замена всего сайта.**  
**Да как целевой контур** для заявок, выдачи защищённых файлов, позднее — API контента или BFF к CMS.

| | Плюсы | Минусы |
|--|-------|--------|
| **Оставить PHP-mailer (+ точечные PHP endpoints)** | Уже работает на REG.RU; дёшево; достаточно для v1 прайса | Сложно масштабировать логику; нет нормальной модели данных; слабый ops |
| **Выделенный backend (Node/другое) на VPS** | Очереди, БД, auth админки, signed URL, единый API | Стоимость, сопровождение, уход с «только FTP-статики» или гибрид |
| **Backend = headless CMS как API** | Редакторы правят контент | Всё равно нужен хостинг CMS + стратегия сборки/ISR/клиента |

**Вывод раздела (v1.1):** полноценный commerce/Node backend **не нужен**. Нужен **контентный контур** (CMS API + при необходимости лёгкий BFF) из‑за журнала, плюс точечный backend для лидов/PDF. Это не «переписать сайт на SSR», а **добавить систему публикации** рядом со статическим фронтом.

## 5. Нужна ли база данных

### 5.1. Сейчас

БД нет. Контент в git, заявки в почте.

### 5.2. Имеет ли смысл подключать БД уже сейчас?

**Отдельная «голая» БД без CMS — не первый шаг.**  
При выносе журнала БД **появится вместе с CMS** (или как её storage) — это ожидаемо и желательно.

Имеет смысл планировать БД явно, когда стартует CMS журнала и/или учёт заявок.

Не нужна БД «ради услуг» или «ради магазина» (магазина не будет; услуг мало).

### 5.3. Что логично хранить в БД (когда появится)

| Данные | Приоритет в БД |
|--------|----------------|
| Заявки | Высокий |
| Статьи, категории журнала | Высокий (через CMS часто = БД) |
| Проекты, отзывы | Высокий |
| Превью прайса / категории цен | Средний–высокий |
| Услуги | Средний (мало записей) |
| SEO-поля сущностей | Вместе с сущностями |
| Настройки сайта | Средний |
| Пользователи админки | При появлении админки |

**Преимущества БД:** целостность, запросы, бэкапы, права, история изменений (с правильным инструментом).

**Издержки:** хостинг, миграции, бэкапы, безопасность.

## 6. CMS

### 6.1. Нужна ли CMS? (v1.1)

**Да — и раньше, чем казалось в v1.0**, именно из‑за журнала (~2 статьи/нед.).

CMS **не** нужна «на весь сайт»:

- услуги и утверждённые витринные страницы могут остаться в коде;
- магазина нет — CMS не для каталога SKU.

CMS нужна как **редакция журнала** (обязательно) и затем **портфолио** (желательно, особенно вместе с медиа).

### 6.2. Варианты (сравнение без финального выбора вендора здесь — выбор в §15)

| CMS | Преимущества | Недостатки | Сложность внедрения | Подходит Анфас? |
|-----|--------------|------------|---------------------|-----------------|
| **Strapi** | Привычный self-host, REST/GraphQL, медиабиблиотека | Нужен сервер, обновления, админка отдельно от статики REG.RU | Средняя | Да, если готов VPS |
| **Payload CMS** | TypeScript-native, гибкие коллекции, хорошо с Next/современным стеком | Self-host; команде нужно освоить модель | Средняя–выше | Да при TS-команде + VPS |
| **Directus** | Быстрый wrap над SQL, права, API | Другая ментальная модель; self-host | Средняя | Да, если важна «БД как основа» |
| **Sanity** | Отличный UX редактора, CDN ассетов, мало ops | SaaS-стоимость, vendor lock, свои правила | Ниже по ops | Да, если не хотят свой сервер CMS |
| **Contentful** | Зрелый SaaS | Дороже, избыточен для малого сайта | Ниже по ops / выше по $ | Сомнительно по цене для масштаба Анфас |
| **WordPress (headless)** | Уже заложен в ARCHITECTURE.md как идея; знаком заказчикам | WP-security/ops; связка со статическим фронтом всё равно нужна | Средняя | Возможно, если у заказчика уже WP-экспертиза |

**Важно для REG.RU:** headless CMS почти наверняка живёт **не** на Host-0 вместе со статикой, либо сайт уезжает на VPS, либо сборка ходит во внешний API на CI.

## 7. Хранение заявок

Сейчас: **только email**.

| Вариант | Преимущества | Ограничения |
|---------|--------------|-------------|
| **Оставить почту** | Уже работает; ноль новой инфры | Нет истории, поиска, статусов, отчётов |
| **PostgreSQL / своя БД** | Полный контроль, воронка, антиспам-логи | Нужен backend + админка/мини-UI |
| **Supabase** | Быстрый старт БД+API+auth | SaaS, модель данных нужно проектировать |
| **CRM (Битрикс24, amoCRM, …)** | Привычный sales-процесс | Интеграция, стоимость, дубли с сайтом |
| **Google Sheets** | Просто для малого потока | Слабая безопасность/надёжность; не для ПДн вдолгую |
| **Strapi / CMS collection «Leads»** | Одна админка с контентом | CMS как CRM — компромисс |
| **Только Telegram-бот** (упомянут в docs как «позже») | Быстрые алерты менеджеру | Не замена учёта |

**Практичный порядок:** почта (как сейчас) → + алерт в мессенджер → при росте лидов — CRM или таблица заявок в БД с простой админкой. Для GDPR/152-ФЗ важно не складывать ПДн в неподходящие «таблички» без политики.

## 8. Хранение изображений

| Вариант | Плюсы | Минусы |
|---------|------|--------|
| **Локально в `public/` + git** (сейчас) | Просто, работает с FTP | Репозиторий и деплои тяжёлые |
| **Локально на хостинге вне git** | Git легче | Ручной FTP, нет версионирования ассетов |

| **Медиабиблиотека CMS** | Редактор грузит сам | Связано с выбором CMS |

**Для Анфас:** краткосрочно — не класть новые тяжёлые исходники в git без необходимости; среднесрочно — CDN/object storage или медиа CMS, особенно для `projects/*/NN.webp`.

## 9. Хранение PDF и документов

Согласовано с продуктовыми ADR прайса:

- Полный прайс **не** в публичной статике с постоянным URL.
- Выдача после заявки по **временной ссылке**.
- Обновление файла — ops-процедура без полного релиза фронта.

| Вариант | Плюсы | Минусы |
|---------|------|--------|
| Файл в `api/private/` на REG.RU + PHP download | Соответствует текущему хостингу | Ручной FTP; бэкапы хостинга |
| Object storage + signed URL | Лучше масштаб и ACL | Нужен backend/сервис подписи |
| CMS media private | Удобно редактору | Сложнее «private + TTL» из коробки |

**Рекомендация в рамках текущей инфры:** private path + PHP (как в DD прайса). После аудита/VPS — рассмотреть object storage.

## 10. Статьи / журнал

Журнал **уже есть** и по плану роста становится **центром SEO**.

При ~2 публикациях в неделю модель «контент в TypeScript» допустима только как **короткий мост** (недели–пара месяцев), не как год работы редакции.

### Целевая архитектура журнала

| Аспект | Рекомендуемая модель |
|--------|----------------------|
| Хранение | CMS/БД, не раздуваемый `articles.data.ts` |
| Редактор | Админка CMS (черновик → публикация) |
| Категории | Справочник тем (уже заложены slug’и) |
| SEO | Поля на записи; URL `/blog/:slug` сохранить |
| Изображения | Медиабиблиотека + CDN |
| Поиск | Фильтр по теме; полнотекст позже |
| Пайплайн | Webhook/CI: публикация → обновление prerender/sitemap |
| Фронт | `articleRepository`: local → HTTP/CMS; маршруты без ломки URL |

**Порог смены (уточнение v1.1):** не «когда станет 20 статей», а **до выхода на стабильные 2 статьи/нед.** — иначе каждый пост будет дорогим релизом.

## 11. Панель администратора

### Нужна ли?

**Не мини-CRM с нуля на React в ближайший спринт.**  
**Да как UI к CMS/заявкам**, когда контент и лиды выходят из почты/git.

### Функционал (при появлении)

Приоритет с учётом роста:

1. **Статьи журнала** (обязательный минимум CMS).  
2. **Проекты + галерея + отзыв** (второй этап).  
3. Заявки (просмотр) — по необходимости sales.  
4. Файлы (PDF прайса) — ops/метаданные.  
5. Услуги — **низкий приоритет** (мало, почти закрытый каталог).  
6. Контент главных страниц — **не тащить в CMS** без нужды (редкие правки).  

Не строить админку под магазин / ЛК / оплату.

## 12. Безопасность

| Тема | Сейчас | Направление |
|------|--------|-------------|
| ENV / секреты | SMTP в `config.local.php`, gitignore | Не тащить секреты в Vite `VITE_*` |
| API | Один публичный `lead.php` | Валидация, honeypot, timing, rate limit; позже — captcha |
| Формы | Honeypot; timing на сервере не до конца задействован клиентом | Довести; не светить внутренние ошибки |
| Загрузка файлов | Нет пользовательских upload | Не открывать upload без auth |
| Выдача PDF | По плану — HMAC + TTL + noindex | Не класть PDF в sitemap |
| Админка (будущее) | Нет | HTTPS, auth, 2FA, минимальные права, аудит |
| `.htaccess` | Запрет чтения config | Сохранить при любых PHP endpoint’ах |

## 13. Производительность

| Тема | Текущий эффект | При выносе контента/медиа |
|------|----------------|---------------------------|
| PageSpeed | Prerender HTML помогает LCP текста; тяжёлые галереи/видео — риск | CDN изображений обычно улучшает |
| SEO | Зависит от актуальности prerender/sitemap | CMS + build-time prerender или SSR на VPS |
| SSR | Сейчас выключен; на REG.RU Node SSR недоступен | Возможен на VPS; не обязателен при хорошем prerender |
| ISR | Нет (это не Next) | Аналог — вебхук CMS → rebuild |
| Кеш | CDN хостинга / браузер | Object storage CDN |
| Время сборки | Растёт с объёмом data+image imports | Вынос медиа из git ускоряет CI |

Предлагаемые эволюции **не требуют** отказа от prerender: статический фронт + API контента на этапе сборки остаётся валидной SEO-стратегией.

## 14. Варианты целевой архитектуры

### Вариант 1. Оставить текущую архитектуру (статика + PHP mailer)

**Что меняется:** только дисциплина (чеклисты, DD прайса на PHP, мелкий рефакторинг долга).

**Плюсы:** минимальная стоимость; уже работает; быстрые релизы UI.  
**Минусы:** контент и медиа через разработчика; заявки в почте; потолок масштаба редакции.

**Когда уместен:** 0–6 месяцев при медленном росте контента.

### Вариант 2. Текущий фронт + усиленный backend на том же/соседнем хостинге

**Что меняется:** больше PHP (или маленький сервис на VPS): заявки в хранилище, PDF token, возможно webhook в CRM; контент пока в git.

**Плюсы:** закрывает лиды/прайс без CMS; использует уже заложенный VPS-путь.  
**Минусы:** контентная боль не исчезает; два контура деплоя при гибриде.

### Вариант 3. Backend + CMS + база данных

**Что меняется:** headless CMS (или WP headless) + БД; фронт ходит в API на build и/или runtime; медиа в CMS/CDN; заявки в БД/CRM.

**Плюсы:** редакция без разработчика; масштаб журнала/портфолио; единая модель контента.  
**Минусы:** стоимость и сложность; REG.RU Host-0 перестаёт быть «единственным» домом для всего; нужна экспертиза ops.

### Вариант 4. Гибрид «контент в CMS, сайт статический, лиды отдельно» (рекомендуемый путь эволюции)

**Что меняется поэтапно:**

1. Сохранить prerender-SPA на текущем хостинге.  
2. Усилить лиды/PDF (PHP или VPS microservice).  
3. Вынести статьи → затем проекты в CMS с build-time fetch на CI.  
4. Медиа — в CMS/CDN.  
5. Админка = CMS; продажи = CRM при росте лидов.

**Плюсы:** не ломает SEO-модель prerender; не требует SSR; заказчик получает редактор; можно остаться на дешёвой раздаче статики.  
**Минусы:** нужен пайплайн «публикация → rebuild»; не «магия realtime» без доп. работы.

## 15. Финальная рекомендация

### 15.1. Оптимальная архитектура для Анфас

**Краткосрочно (сейчас → ~3–6 месяцев):**  
**Вариант 1 + элементы Варианта 2** — оставить статику + prerender + PHP для заявок и защищённого прайса; навести порядок в долге (цены, sitemap/prerender, FSD, Metrika goals).

**Среднесрочно (по мере роста журнала/портфолио/редакции):**  
**Вариант 4 (гибрид)** — headless CMS + БД для **статей и проектов**, сборка фронта с подтяжкой контента, CDN для медиа, заявки в CRM или БД, статика по-прежнему раздаётся дёшево.

**Не рекомендуется немедленно:** полный переезд на SSR-монолит «ради моды» или дорогой enterprise CMS при текущем объёме.

### 15.2. Почему так

| Критерий | Как закрывается |
|----------|-----------------|
| Развитие сайта | UI и SEO уже сильны; узкое место — редакция и медиа, не «не тот фреймворк» |
| SEO | Prerender уже даёт индексируемый HTML; его надо сохранить при выносе контента |
| Масштаб | CMS+CDN решают статьи/проекты; PHP/CRM — лиды |
| Поддержка | Заказчик правит тексты в CMS; разработчик — продукт и дизайн-систему |
| Производительность | Статика + CDN обычно быстрее тяжёлого SSR на слабом VPS |
| Стоимость | Не платить за платформу раньше боли; VPS/CMS — когда боль измерима |
| Удобство заказчика | Админка CMS понятнее, чем PR в TypeScript |
| Техдолг | Repository-интерфейсы уже готовят замену `local*`; их использовать, а не выкидывать |

### 15.3. Что переиспользовать обязательно

- FSD-слои и pattern repository (`article` / `project` / `service`).  
- Единый контур заявок (`BriefModal` / `submitLead` / `lead.php`).  
- `createSeoMeta`, prerender, sitemap-дисциплину.  
- Design Document прайса: private PDF + форма + письмо, без публикации полного прайса.  
- Заготовку VPS/Docker — когда понадобится CMS/API рядом со статикой.

### 15.4. Порядок работ (рекомендуемый)

1. Зафиксировать этот аудит и DD прайса.  
2. Реализовать прайс в рамках **текущей** архитектуры (без CMS).  
3. При росте редакции — пилот CMS **только на журнале**.  
4. Затем проекты/медиа.  
5. Заявки: почта → CRM/БД по объёму лидов.
