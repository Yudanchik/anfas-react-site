# Сопровождение раздела «Прайс-лист» (PDF, ссылки, письма)

Операционная инструкция для сотрудника, который заменяет полный PDF прайс-листа
на сервере, и для разработчика, который настраивает или переносит окружение.

Бизнес-требования и архитектура раздела описаны в
[`docs/architecture/price-list.md`](architecture/price-list.md) — этот документ их не
пересматривает, а только описывает конкретные операционные шаги.

## 1. Как это устроено (кратко)

```
Пользователь на /prices или /prices/:categorySlug
  → форма «Получить полный прайс» (intent="price-list")
  → POST /api/lead.php
      → письмо в офис (заявка получена)
      → генерация временной HMAC-ссылки на скачивание
      → письмо клиенту со ссылкой (текст + HTML)
  → клиент переходит на /prices/thanks
  → клиент переходит по ссылке из письма
  → GET /api/price-download.php?id=...&exp=...&sig=...
      → проверка подписи и срока действия
      → отдача PDF (Content-Disposition: attachment)
```

Ключевые принципы (не меняются без пересмотра `docs/architecture/price-list.md`):

- Полный PDF **никогда** не публикуется по постоянному открытому URL и не хранится в
  `public/` или в собранной статике сайта.
- Скачивание возможно только по временной подписанной ссылке, которую пользователь
  получает на почту после успешной заявки.
- `config.local.php`, сам PDF и файлы rate-limit **не коммитятся в git** и не
  собираются вместе со статикой сайта.

## 2. Где хранится исходный PDF

### 2.1. Файл, который скачивают пользователи (боевой прайс)

Полный PDF прайс-листа, который уходит пользователям по ссылке из письма, хранится
**на сервере хостинга, вне web root** — то есть вне папки, которая отдаётся сайтом
напрямую (`build/client` / корень FTP-доступа). Абсолютный путь к этому файлу
указывается в `config.local.php` в параметре `price_pdf_path` (см. раздел 3).

Пример структуры на REG.RU (Host-0):

```text
/home/USER/www/anfas-remont.ru/        ← web root, сюда деплоится build/client
/home/USER/www/dev.anfas-remont.ru/    ← web root dev-стенда
/home/USER/private/anfas-price.pdf     ← боевой PDF прода, вне web root
/home/USER/private-dev/anfas-price.pdf ← боевой PDF dev-стенда, вне web root
```

Точные пути зависят от тарифа и панели хостинга — уточняются в файловом
менеджере / по FTP при первой настройке и фиксируются в `config.local.php`.

**Требования к расположению:**

- Каталог с PDF не должен находиться внутри web root сайта (недоступен по прямому
  `https://.../anything.pdf`).
- Если хостинг технически не позволяет вынести файл за пределы web root — каталог
  обязательно закрывается на уровне `.htaccess` (`Deny from all` / `Require all
  denied`) по аналогии с `public/api/.htaccess` для `config.local.php`.
- У dev и prod — **разные** файлы и пути. Нельзя обновлять прод, подкладывая файл в
  dev-каталог, и наоборот.

### 2.2. Исходник, использованный при наполнении сайта (не путать с боевым PDF)

В `resources/source-documents/` репозитория лежит PDF, который использовался один
раз на этапе 1 для ручного наполнения превью-данных (`src/entities/price/model/prices.data.ts`).
Он не связан с `price-download.php`, не разворачивается на сервере и не обновляется
при замене боевого прайса. Трогать его нужно только при плановом пересмотре
публичных превью-цен на сайте (см. раздел 6).

## 3. Параметры `config.local.php`

Файл `public/api/config.local.php` создаётся вручную на каждом сервере (prod и dev
— отдельно) и **не коммитится**. Шаблон — `public/api/config.example.php`.

Общие параметры формы лидов (`to`, `from`, `from_name`, `smtp`, `min_submit_seconds`)
описаны в [`docs/LEAD_FORM_EMAIL.md`](LEAD_FORM_EMAIL.md). Ниже — параметры,
относящиеся именно к прайс-листу.

| Параметр | Назначение |
|---|---|
| `price_pdf_path` | Абсолютный путь на файловой системе сервера к боевому PDF прайс-листа (см. раздел 2.1). Используется только `price-download.php` для стриминга файла. |
| `price_link_secret` | Случайный секрет для HMAC-подписи ссылки на скачивание (`hash_hmac('sha256', ...)`). Должен быть длинной случайной строкой (от 32 символов), уникальной для каждого окружения (prod ≠ dev). Генерируется один раз командой `bin2hex(random_bytes(32))` в PHP-консоли сервера. Утечка секрета = возможность подделать ссылку на скачивание. |
| `price_link_ttl` | Срок жизни ссылки на скачивание, в секундах. Ориентир — `86400` (24 часа). Определяет, через сколько времени сгенерированная ссылка перестаёт открывать файл (см. раздел 4.2). |
| `public_site_url` | Публичный адрес сайта (`https://anfas-remont.ru` на проде, адрес dev-стенда — на dev). Нужен, чтобы `lead.php` собрал абсолютную ссылку на `price-download.php` для письма клиенту. |
| `price_rate_limit.max_requests` | Сколько заявок на прайс-лист разрешено с одного IP за `window_seconds`. Ориентир — `5`. |
| `price_rate_limit.window_seconds` | Длина окна ограничения частоты запросов, в секундах. Ориентир — `3600` (1 час). |
| `price_rate_limit.storage_path` | Путь к writable-каталогу для файловых счётчиков rate limit. Хранит только HMAC-хэши IP (не сами адреса), сам каталог должен быть **вне web root** и доступен на запись пользователю, от которого выполняется PHP. |

Все пути (`price_pdf_path`, `price_rate_limit.storage_path`) и секрет
(`price_link_secret`) обязаны быть **разными на dev и на prod**. Использование
одного секрета или одного пути на двух окружениях обесценивает изоляцию сред.

## 4. Механизм выдачи файла

### 4.1. HMAC-подписанная ссылка

Ссылка на скачивание не хранится в базе данных — её не существует до заявки, она
собирается на лету в `buildPriceDownloadLink()` (`public/api/lead.php`) и
самодостаточна:

```
/api/price-download.php?id={id}&exp={exp}&sig={sig}

id  = bin2hex(random_bytes(16))                  — случайный идентификатор
exp = unix-время истечения (time() + price_link_ttl)
sig = hash_hmac('sha256', "{id}|{exp}", price_link_secret)
```

При обращении `price-download.php` пересчитывает `sig` по тем же `id`/`exp` и
секрету из `config.local.php` и сравнивает результат через `hash_equals()`
(timing-safe сравнение — устойчиво к атакам по времени ответа). Подмена любого из
трёх параметров (`id`, `exp`, `sig`) ломает подпись, и ссылка становится
недействительной (`403`).

Ссылка не содержит имени, телефона или email пользователя — только техническую
пару «идентификатор + срок + подпись».

### 4.2. TTL (срок действия ссылки)

- Срок действия задаётся `price_link_ttl` (в секундах) в момент генерации ссылки —
  не хранится отдельно, вычисляется как `exp = time() + price_link_ttl` и передаётся
  в самой ссылке.
- Если на момент перехода `exp < time()`, `price-download.php` отвечает `410 Link
  expired` и не отдаёт файл.
- Просроченная ссылка не продлевается и не работает даже с верной подписью —
  единственный способ получить новую ссылку — повторно отправить форму на сайте
  (ADR-08 в `docs/architecture/price-list.md`).
- Увеличение `price_link_ttl` увеличивает окно, в течение которого пересланная
  третьим лицам ссылка остаётся рабочей — сознательно выбирать значение, а не
  ставить «на всякий случай» большим.

### 4.3. Dual-mail (два письма на одну заявку)

На одну успешную заявку `intent="price-list"` `lead.php` отправляет **два
отдельных письма**:

1. **Письмо в офис** (`to` из `config.local.php`) — как у обычных заявок, с
   пометкой «Тип заявки: запрос полного прайс-листа», именем, телефоном и email
   заявителя. Отправляется первым.
2. **Письмо клиенту** (на email из формы) — со ссылкой на скачивание, сроком
   действия и телефоном компании. Отправляется вторым, отдельным SMTP/`mail()`
   вызовом, в формате `multipart/alternative` (текстовая версия + HTML-версия в
   одном письме — почтовый клиент сам выбирает, что показать).

Важно про порядок и обработку ошибок (см. `public/api/lead.php`):

- Ссылка на скачивание собирается **до** отправки обоих писем — если она не
  собралась (не настроен `price_pdf_path` / `price_link_secret` /
  `public_site_url`), заявка завершается ошибкой `503` и ни одно письмо не
  уходит.
- Если письмо в офис не отправилось — заявка завершается ошибкой `502`, письмо
  клиенту не отправляется (нет смысла обещать файл, если офис не узнал о лиде).
- Если письмо в офис отправилось, а письмо клиенту — нет, API отвечает `502` с
  отдельным текстом ошибки, но **уже отправленное письмо в офис не отменяется** —
  компания в любом случае узнаёт о заявке, даже если клиент увидит ошибку и
  напишет/позвонит напрямую.

## 5. Замена боевого PDF

### 5.1. Порядок действий (atomic replace)

Файл нельзя перезаписывать напрямую под тем же именем, пока по нему потенциально
идёт скачивание — иначе пользователь может получить оборванный/частично
загруженный файл. Порядок:

1. Загрузить новый файл на сервер **под временным именем**, например
   `anfas-price.pdf.new`, в тот же каталог, что указан в `price_pdf_path`.
2. Убедиться, что загрузка полностью завершена (сравнить размер файла с
   исходником, при возможности — контрольную сумму).
3. Переименовать (`rename`) старый файл в резервную копию, например
   `anfas-price.prev.pdf` (через FTP-клиент/файловый менеджер — операция
   переименования, а не удаления).
4. Переименовать `anfas-price.pdf.new` в имя, указанное в `price_pdf_path`.
5. Только после этого при необходимости удалить более старую резервную копию
   (хранить минимум одну предыдущую версию — см. откат в разделе 5.3).

Переименование — атомарная операция на уровне файловой системы, поэтому
`price-download.php` в любой момент видит либо полностью старый, либо полностью
новый файл, никогда — наполовину загруженный.

### 5.2. Обязательные проверки после замены

После каждой замены файла на **каждом** окружении (dev и prod по отдельности)
пройти по списку:

1. **Права доступа**: файл читаем PHP-процессом (`is_readable`), каталог
   по-прежнему недоступен по прямому публичному URL.
2. **Заявка end-to-end**: отправить тестовую заявку на прайс через реальную форму
   на сайте (`/prices` → «Получить полный прайс»).
3. **Письмо в офис**: пришло, с пометкой про запрос прайса и корректными данными
   заявителя.
4. **Письмо клиенту**: пришло на указанный тестовый email (проверить и «Спам»),
   ссылка кликабельна, текстовая и HTML-версия читаемы.
5. **Валидная ссылка**: переход по ссылке из письма отдаёт **новый** файл (не
   старую версию из кэша хостинга/CDN, если он есть).
6. **Подмена подписи**: вручную изменить один символ в `id`, `exp` или `sig` в
   ссылке из письма → ожидается `403`, файл не отдаётся.
7. **Истечение TTL**: либо дождаться истечения `price_link_ttl`, либо на
   dev-стенде временно поставить маленький `price_link_ttl` (например, `30`),
   получить ссылку, подождать и убедиться, что после истечения срока ответ —
   `410`, а не файл.
8. **Повторный запрос**: после «протухшей» ссылки отправить форму ещё раз и
   убедиться, что новая заявка выдаёт новую рабочую ссылку.
9. **Direct URL**: убедиться, что прямой путь к PDF на файловой системе
   недоступен по HTTP (например, попытка обратиться к нему по URL, повторяющему
   структуру `price_pdf_path`, если каталог случайно оказался внутри web root, —
   должна возвращать `403`/`404`, а не файл).

### 5.3. Откат (rollback)

Если после замены обнаружилась проблема (битый файл, не тот прайс, ошибка
конвертации):

1. Переименовать текущий (проблемный) файл в `anfas-price.broken.pdf` (не
   удалять сразу — пригодится для разбора причины).
2. Переименовать резервную копию предыдущей версии (`anfas-price.prev.pdf`,
   см. шаг 3 в разделе 5.1) обратно в имя из `price_pdf_path`.
3. Повторить проверку по списку из раздела 5.2 (минимум пункты 5, 3, 4).
4. Только после подтверждения, что откат работает, разбираться с
   `anfas-price.broken.pdf` — как с проблемным файлом, не через боевой путь.

Именно поэтому в разделе 5.1 предыдущая версия не удаляется сразу, а
переименовывается: без резервной копии откатиться некуда.

## 6. Процесс сопровождения после обновления прайса

1. **Кто.** Сотрудник компании с доступом к хостингу (FTP / файловый менеджер),
   без участия разработчика — если меняются только цифры внутри существующих
   категорий, а не структура раздела.
2. **Как часто.** Файл заменяется по мере изменения цен у заказчика — это
   регулярная операционная задача, не привязанная к релизам сайта.
3. **Что не требует релиза сайта.** Сама по себе замена PDF (шаги раздела 5) не
   требует пересборки/деплоя фронтенда — превью на сайте и боевой файл обновляются
   независимо.
4. **Когда требуется участие разработчика.** Публичное превью на сайте
   (`src/entities/price/model/prices.data.ts` — категории, позиции, цены «от»,
   FAQ) обновляется **не при каждой правке файла**, а при существенном изменении
   ориентиров или состава работ (см. §1.11 `docs/architecture/price-list.md`).
   В этом случае нужен обычный цикл: правка данных → `pnpm check` → `pnpm build` →
   деплой через `dev`/`main`.
5. **Дата/редакция.** Если требуется явно показывать пользователю «актуально
   на …», дата редакции ведётся отдельно на стороне сотрудника/в`config.local.php`-
   комментарии как заметка — на данный момент отдельного поля в UI под это не
   заведено (вне объёма текущей реализации).
6. **Ротация `price_link_secret`.** Плановая или внеплановая (при подозрении на
   утечку) смена секрета делает недействительными **все ранее выданные, ещё не
   истёкшие ссылки** — пользователям, которые запросили прайс незадолго до
   ротации, придётся запросить его заново. Менять секрет можно в любой момент
   правкой `config.local.php`, релиз фронтенда не требуется.

## 7. Деплой и файлы, которые не должны попадать в git/деплой

- `public/api/config.local.php`, боевой PDF (раздел 2.1) и каталог
  `price_rate_limit.storage_path` **никогда** не коммитятся и не входят в
  `build/client` — деплой статики сайта (см.
  [`deploy/regru-hosting/README.md`](../deploy/regru-hosting/README.md)) их не
  трогает, потому что они физически не участвуют в сборке и лежат вне web root.
- После деплоя новой версии фронтенда `config.local.php` на сервере **не
  пересоздаётся** — он создаётся один раз при первичной настройке окружения
  (см. `docs/LEAD_FORM_EMAIL.md`) и переживает обновления сайта.
- Если на сервере пришлось временно расположить приватный каталог внутри web
  root (ограничение конкретного хостинга) — обязателен `.htaccess` с запретом
  доступа, как для `public/api/.htaccess`, и это отдельно фиксируется в
  инструкции конкретного окружения.
