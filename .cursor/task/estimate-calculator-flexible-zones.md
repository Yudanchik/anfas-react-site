## 1. Проблема

Сценарии вроде «Демонтаж покрытия» включают **один** вариант и через **conflict groups** выключают остальные альтернативы того же типа.

На объекте часто несколько зон с **разными** покрытиями и площадями, например:

- 20 м² демонтаж ламината (комната);
- 5 м² демонтаж плитки (санузел);
- 12 м² демонтаж линолеума (коридор).

То же для **укладки чистового покрытия** (это **работа**, не материал): кварц на кухне, ламинат в комнате, плитка в коридоре.

Сейчас сметчик вынужден:

- либо вручную крутить одну строку mapping и терять разбивку по зонам;
- либо плодить «Ручные строки» без привязки к прайсу;
- либо после сценария вручную снова включать «выключенные» альтернативы — неудобно и легко ошибиться.

**Цель дизайна:** оставить сценарии для типового пакета на объект, добавить быстрый способ **добавлять отдельные зональные строки из прайса**, которые **не затирают** уже добавленные.

## 2. Текущая модель (как есть)

### Presets / scenarios

- Полы: `applyFloorPreset` → набор `priceKey` + quantity + `disableConflictingAlternatives`.
- Стены: `applyWallScenario` / `resolveWallScenarioKeys` + `disableWallConflictingAlternatives`.
- Manual rows (`source: 'manual'`) conflict **не трогает**.

### Conflict groups (полы) — жёсткость

`FLOOR_CONFLICT_GROUPS` (фрагмент):

- `demolition-covering` — все типы покрытия (ламинат, линолеум, плитка, паркет, …) **взаимоисключающие**;
- `demolition-screed`, `screed-main`, `waterproofing-acrylic-layers`, `self-leveling-device`, `waste-trip` — аналогично «один активный вариант».

Итог: в таблице есть **по одной canonical-строке** на `priceKey` (`id = floors:<priceKey>`). Нельзя иметь две включённые строки «Демонтаж ламината» с разными объёмами/комментариями без клонов.

### Manual lines

`createManualEstimateLine`: уникальный `id` / `priceKey` вида `manual-N`, `source: 'manual'`, цена/название вручную.
Попадают в итог и persistence. **Минус:** нет стабильной связи с mapping/прайсом, нет автоцены при обновлении прайса.

### Persistence

Сериализует все строки; для `manual` сохраняет title/unit/kind.
Canonical mapping-строки восстанавливаются патчами по `id`/`priceKey`.
**Зональные клоны** потребуют явной сериализации title/unit (как manual) или восстановления из mapping по `priceKey` + уникальный `id`.

### Формулы

Без изменений: `round(qty × price × coef)`. Материалы не считаем.

### 3.3. Плитка пола (labour облицовки)

В frontend — категория `plitka` (не `napolnye`): облицовка пола/стен плиткой и керамогранитом, раскладка, затирка, надбавки.
В PDF — соответствующий плиточный блок.
Для зональной укладки «плитка в коридоре» — это **отдельный whitelist** (не путать с демонтажем плитки пола, который уже в floors mapping).

### 3.4. Плинтус (монтаж — labour)

В PDF большой блок монтажа напольного плинтуса (дюрополимер, МДФ, пластик, алюминий, теневой и т.д.) + подрезки/углы/герметик.
В `prices.data.ts` публичного «Монтаж плинтуса …» почти нет (есть демонтаж плинтуса, ниши/плоскости под скрытый, плиточные бордюры).
**Рекомендация Stage:** плинтус — optional follow-up из PDF; MVP зон можно начать без полного блока плинтуса.

### 3.5. Порожки / профили

Отдельной явной позиции «монтаж порожка» в выборке frontend/`napolnye` не найдено; в PDF ближе «подгонка покрытия в зоне примыкания к плитке или профилю» (м. пог.).
**Open:** уточнить у сметчиков, нужна ли отдельная строка порожка, или хватает примыкания + ручная строка.

### 3.6. Линолеум — укладка

**Демонтаж** линолеума есть (frontend + PDF + floors mapping).
**Укладка линолеума** как отдельная labour-позиция в `napolnye-pokrytiya` и в PDF-выборке **не найдена**.
→ Не выдумывать; при необходимости — ручная строка или отдельный вопрос к прайсу.

### 3.7. Вывод по материалам

Позиции раздела напольных покрытий / плитки / плинтуса в прайсе — **расценки работ**. Отделить labour от материалов можно. **Stop condition по материалам не срабатывает.**

В `FLOOR_PRICE_MAPPING` чистовой монтаж **намеренно исключён** комментарием — это продуктовый MVP, не отсутствие в прайсе.

## 4. Варианты архитектуры

| # | Идея | Плюсы | Минусы |
|---|------|-------|--------|
| A | Ослабить conflict groups (разрешить несколько enabled canonical) | Мало кода | **Не решает** две зоны одного типа (одна строка = один qty) |
| B | Только manual lines + подсказки | Уже работает | Нет цены из прайса, дубли названий, ошибкоопасно |
| C | **Zoned clone lines** из mapping/whitelist | Несколько зон одного типа; цена из прайса; сценарии остаются | Нужен origin/id; persistence; UI блок; conflict не трогает клоны |
| D | Полноценная модель «Room / Zone» entities | Макс. гибкость | Большой refactor EstimateLine / UI — **stop condition** |

**Рекомендация: C** (без ломки presets и без смены формулы).

## 5. Рекомендуемая модель: zoned duplicate lines

### Типы строк (логически)

| Тип | Как появляется | `id` | `priceKey` | Conflict | Persistence |
|-----|----------------|------|------------|----------|-------------|
| **Canonical mapping** | `build*EstimateLines` | `floors:<priceKey>` | catalog id | Участвует в conflict при **preset** | Патч enabled/qty/… |
| **Scenario-enabled** | Тот же canonical, `enabled=true` после пресета | как canonical | catalog | Preset глушит siblings | как canonical |
| **Manual custom** | «Ручная строка» | `floors:manual-N` | `manual-N` | Нет | title/unit/kind |
| **Zoned clone** | «Добавить работу по зоне» | `floors:zone-<priceKey>-<n>` | **тот же catalog id** | **Не** участвует в disable siblings; не глушит canonical | Как manual + `priceKey` для восстановления цены/title из mapping при hydrate |

Опциональное поле (минимальный touch типов), если понадобится явно:

- `origin?: 'mapping' | 'manual' | 'zone'`
или эвристика: `id` содержит `:zone-` / `source` расширить до `'zone'` **без** смены формулы.

**Не обязательно** ломать `EstimateLine` целиком: достаточно уникального `id` + правила conflict «только canonical id» + serialize zone как «известная по priceKey + свои qty/comment».

### Поведение

1. Сценарии **не меняем** по смыслу (один типовой пакет / один выбор в карточке).
2. «Добавить по зоне» **клонирует** позицию из whitelist (демотаж / укладка / опционально гидро), ставит qty + comment (зона), `enabled: true`.
3. Уже существующие строки **не перезаписываются**.
4. Conflict при добавлении зоны **не вызывается** (или вызывается только если когда-нибудь включим zone через preset — не делаем).
5. Quick actions по-прежнему пишут qty в matching lines — **осторожно:** сейчас матч по `kind`/`unit` заденет и клоны. Для Stage 1 зон: либо исключить `origin=zone` из bulk apply, либо применять bulk только к canonical. **Зафиксировать в реализации.**

### Finish labour в mapping

Новая группа в floors (или подмножество whitelist только для zone-picker), например kind `finish-floor` / group «Чистовое покрытие»:

- MVP whitelist: подложка, плавающая укладка, клей-варианты кварца, подготовка/монтаж инженерки (короткий список из frontend + 2–3 PDF-дополнения).
- Плитка пола — отдельная подгруппа или phase 2.
- Плинтус / порожки — phase 2 после подтверждения.

Assert `source=both` где есть frontend.

## 6. UX (полы) — компактно

Не wizard. Один компактный блок под сценариями / рядом с ручной строкой:

**«Добавить работу по зоне»**

1. Select **категория:** Демонтаж покрытия | Укладка покрытия | Гидроизоляция (опционально сразу / phase 1.5).
2. Select **вариант** (из whitelist этой категории).
3. Поле **площадь / метраж**.
4. Поле **зона** (текст → уходит в комментарий строки, напр. «санузел»).
5. Кнопка **«Добавить в смету»** → сразу enabled строка в таблице (группа по kind / «Зональные» / рядом с canonical).

Отдельные ярлыки-кнопки (короткие) допустимы:

- «+ Демонтаж по зоне»
- «+ Укладка по зоне»

без раздувания страницы (один раскрывающийся panel).

Сценарии остаются «быстрый черновик на весь объект»; зоны — «добавить кусок сметы».

## 7. Стены — риски (без реализации)

Та же жёсткость:

- `demolition-covering` — один тип демонтажа;
- `wallpaper-type` / `paint-layers` — один финиш;
- сценарий «с нуля» — один пакет на все стены.

Реальные кейсы: разные комнаты (обои vs краска), несколько демонтажей, локальная штукатурка + общий пакет.

**Рекомендация:** после пилота зон на полах **переиспользовать** тот же `createZonedLineFromMapping` для стен.
Не плодить вторую модель. Не ослаблять wall conflicts вслепую до появления zone clones.
