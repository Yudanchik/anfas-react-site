# Anfas Renovation

Сайт компании по ремонту и интерьеру. Этот README — живое ТЗ и рабочая дорожная карта проекта.

Цель документа:

- зафиксировать, что именно мы строим;
- держать в одном месте требования к дизайну, структуре, аналитике и SEO;
- работать итерациями: `feature` → `dev` → `main`.

## 1. Цель проекта

Сделать лендинг/сайт, который:

- сразу показывает, что компания реально занимается ремонтом;
- снимает страхи и негатив вокруг ремонта;
- подводит пользователя к выбору между двумя сценариями:
  - ремонт по дизайн-проекту;
  - пакетное предложение / готовое решение;
- ведёт к целевому действию:
  - оставить заявку;
  - получить расчёт;
  - получить консультацию;
  - выбрать подходящий формат ремонта.

## 2. Целевая аудитория

Основные сегменты:

- родители, покупающие квартиру детям;
- люди, которые находятся далеко и не могут лично контролировать ремонт;
- клиенты, которым нужен один подрядчик на весь процесс;
- заказчики, которым важны сроки, фиксированность и прозрачность;
- люди, которые хотят понятный результат без хаоса и неопределённости.

## 3. Главная идея подачи

Не просто рассказывать о ремонте, а показывать его на примерах.

Нужны:

- реальные или стилизованные визуализации интерьеров;
- примеры выполненных объектов;
- визуальный акцент на доверие, прозрачность и контроль;
- спокойная, уверенная подача без лишней воды.

## 5. Структура сайта

### 5.1 Первый экран

Задача экрана:

- сразу объяснить, чем занимается компания;
- показать уверенность и визуальную силу;
- дать первый CTA.

Содержимое:

- короткий оффер о ремонте;
- сильная визуализация интерьера / примеры объектов;
- кнопки:
  - `Рассчитать ремонт`;
  - `Выбрать формат ремонта`;
  - `Получить консультацию`.

### 5.2 Блок боли клиента

Формат: слева проблемы, справа решения компании.

Боли:

- просрочка сроков;
- непредсказуемый итоговый бюджет;
- неясно, что происходит на объекте;
- сложность контроля, особенно если клиент далеко;
- страх получить некачественный результат.

Решения:

- прозрачный процесс;
- понятные сроки;
- фиксируемые этапы;
- отчёты и фото/видео с объекта;
- контроль через приложение;
- снижение рисков.

### 5.3 Блок с двумя направлениями

Нужно показать два сценария работы:

- ремонт по дизайн-проекту;
- пакетное предложение / готовое решение.

Для каждого сценария указать:

- кому подходит;
- ключевые особенности;
- чем отличается от другого варианта;
- почему это хороший выбор.

### 5.4 Блок сравнения форматов

Сравнение можно сделать в виде:

- таблицы;
- двух больших карточек;
- гибридного решения.

Сравнить:

- сроки;
- стоимость;
- степень вовлечённости клиента;
- гибкость;
- предсказуемость;
- кому подходит;
- что входит.

### 5.5 Блок выбора

После сравнения пользователь должен ответить себе на вопрос:

- что ему ближе?

Следующий шаг:

- если индивидуальный ремонт — оставить заявку / обсудить проект;
- если пакетное решение — перейти в мини-калькулятор.

### 5.6 Мини-калькулятор для пакетного решения

Калькулятор делаем только для пакетного предложения.

Базовые поля:

- площадь;
- тип квартиры / помещения;
- уровень комплектации;
- дополнительные опции.

Результат:

- ориентировочная стоимость;
- примерный срок;
- кнопка заявки.

### 5.7 Блок про процесс работы

Важно показать, что ремонтом можно управлять прозрачно и удалённо.

Нужно визуально передать:

- этапы работ;
- баланс / состояние проекта;
- отчёты;
- фото и видео с объекта;
- коммуникацию через приложение;
- контроль со стороны клиента.

### 5.8 FAQ

Нужен отдельный блок с часто задаваемыми вопросами.

Смысл блока:

- снять типовые возражения;
- закрыть вопросы по срокам, стоимости, гарантиям и контролю;
- поддержать SEO через полезный текст.

### 5.9 Блок партнёров

Нужен блок `Наши партнёры`.

Требования:

- сетка с логотипами партнёров;
- аккуратный современный вид;
- анимация, похожая на ticker / бегущую линию;
- визуальная динамика без ощущения рекламы.

### 5.10 Блок соцсетей

Нужен отдельный блок, который:

- показывает соцсети компании;
- мотивирует подписаться;
- помогает людям увидеть реальные проекты и процессы.

Желательно:

- короткий сильный заголовок;
- 2–3 предложения о пользе подписки;
- кнопки на Instagram, Telegram, YouTube и другие актуальные каналы;
- визуальная подача в стиле референсов с акцентом на доверие.

### 5.11 Финальный CTA

Финальный экран должен добивать пользователя до действия:

- оставить заявку;
- получить консультацию;
- рассчитать стоимость;
- подобрать формат ремонта.

## 6. УТП и акценты

Обязательно транслируем:

- ремонт без хаоса;
- понятные сроки;
- прозрачный процесс;
- удобный контроль через приложение;
- два понятных сценария для разных типов клиентов;
- для пакетного решения:
  - готовые решения;
  - быстрее;
  - фиксированнее;
  - проще в выборе.

## 7. SEO-задачи

Для пакетного направления нужен отдельный SEO-акцент.

Перед написанием текстов нужно отдельно проверить актуальные и частотные поисковые формулировки по теме ремонта, а затем встроить их в структуру без переспама.

В тексты и структуру нужно органично встроить ключевые формулировки:

- ремонт под ключ;
- готовые решения по ремонту;
- пакетный ремонт квартиры;
- ремонт с фиксированной ценой;
- ремонт с понятными сроками.

Желательно добавить отдельный SEO-блок с:

- преимуществами;
- сценариями применения;
- объяснением, кому подходит пакетное решение.

Также для каждого ключевого маршрута сайта нужно делать SEO-оптимизацию:

- главная страница;
- страница услуг;
- страницы проектов;
- страница контактов;
- страница о компании;
- страница FAQ;
- страница пакетного решения;
- страница ремонта по дизайн-проекту.

Для каждой страницы фиксируем:

- уникальный title;
- unique description;
- H1;
- SEO-тексты;
- внутренние ссылки;
- изображения с понятными alt;
- при необходимости отдельный информационный блок под поисковый запрос.

## 8. Тон и подача

Тон общения сайта:

- спокойный;
- уверенный;
- конкретный;
- без пафоса;
- без абстрактных обещаний.

Не продаём ремонт в лоб. Снимаем страхи и показываем системность.

## 9. Дизайн-ограничения

Визуально важно:

- реальные интерьеры или качественные визуализации;
- сравнительные блоки;
- иконки / маркеры болей и решений;
- акцент на прозрачность и контроль;
- адаптивная мобильная версия без перегруза.

Если для какого-то блока пока нет готовых изображений, допускается временный серый плейсхолдер с подписью вида:

- `тут будет картинка`;
- `тут будет визуализация`;
- `тут будет фото объекта`.

Такой плейсхолдер остаётся до момента, пока не будет подставлен реальный контент.

Контентные требования:

- наполняем весь сайт SEO-оптимизированным текстом;
- добавляем изображения и визуальные материалы на все важные страницы;
- если изображения не готовы, не блокируем разработку, а оставляем аккуратные заглушки;
- текст и картинки должны поддерживать доверие, а не быть просто декоративными.

Адаптивность:

- все экраны должны корректно работать от `320px`;
- на мобильных шрифт не должен опускаться ниже `12px`;
- CTA должны оставаться заметными и доступными;
- не должно быть горизонтального скролла;
- блоки должны перестраиваться без потери смысла.

## 12. Архитектура проекта

Проект ведём по FSD-подобной структуре:

- `src/app` — провайдеры и глобальная инициализация;
- `src/routes` — страницы и маршруты;
- `src/widgets` — крупные блоки интерфейса;
- `src/features` — пользовательские сценарии;
- `src/entities` — сущности бизнеса;
- `src/shared` — переиспользуемые UI, хуки, стили и утилиты.

Базовый принцип зависимостей:

`routes` → `widgets` → `features` → `entities` → `shared`

Нижний слой не должен импортировать верхний.

## 14. Git workflow

Работаем через три ветки:

- `main` — стабильная версия для релиза;
- `dev` — интеграционная ветка разработки;
- `feature/*` — короткие ветки под отдельные задачи.

Правило работы:

1. создаём ветку от `dev`;
2. делаем одну понятную задачу;
3. пушим в GitHub;
4. сливаем `feature/*` в `dev`;
5. после проверки и стабилизации сливаем `dev` в `main`.

Рекомендуемый нейминг:

- `feature/hero-redesign`;
- `feature/footer-redesign`;
- `feature/faq-block`;
- `feature/partners-ticker`;
- `feature/socials-section`;
- `feature/seo-package-block`;
- `feature/calculator-package`.
